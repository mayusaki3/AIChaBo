# AIChaBo コア仕様 概要（確認用）

本書は、AIChaBo の「コア部分」を **実装から独立して**整理し、  
旧コードと AI 生成コードが混在している状況でも、仕様として整合性確認を進められるようにするための **確認用仕様**である。

本書の目的：
- コアが提供すべき機能・責務・入出力・永続化・安全条件を、別角度（設計仕様）で定義する
- 既存実装（旧/AI生成）と照合するための **チェックリスト**を提供する

---

## 1. コアの定義（ここでの “コア”）
本プロジェクトでは、次をコアと定義する。

- UI（Discord 等）や AI プロバイダ（OpenAI/Gemini/Claude）に依存しない共通機能
- 認証情報（APIキー等）を安全に扱う仕組み
- スレッド（会話単位）の状態管理
- チャット実行ループ（入力→文脈→LLM呼び出し→ツール→出力）
- Web 取得（検索/読み取り）や添付管理など、チャット処理に必要な共通ユーティリティ

実装上の目安：
- `common/*` が中心（ただし `ai/*` と `ui/*` の境界条件も仕様として定義する）

---

## 2. レイヤと責務（仕様上の境界）

### 2.1 共通層（common）
共通層は以下のサブドメインを持つ。

- secret（秘密ストア）
  - APIキー等の機密情報を暗号化して保存/取得/削除する
  - JSON破損や不正構造に対し自己修復し、運用停止を回避する
- session（セッション/スレッド文脈）
  - ユーザー単位/サーバー単位の状態と、スレッド文脈を管理する
- chat（チャット中核）
  - provider/model の正規化、認証解決、チャットループ、継続制御、共有認証の適用など
- utils（共通ユーティリティ）
  - redact/logger/jsonc/file_io/attachments/prefetch/thread_utils/webread_utils など

### 2.2 AI層（ai）
- プロバイダ別の API 呼び出し実装（OpenAI/Gemini/Claude）
- 画像認識/画像生成などのプロバイダ差を吸収する
- common から見た I/F は「抽象化された provider 呼び出し」であること

### 2.3 UI層（ui）
- Discord コマンド、スレッド生成/招待/退出などのプラットフォーム固有処理
- common に対しては「入力イベント」「出力メッセージ」「添付」「コマンド呼び出し結果」を渡すだけであること

---

## 3. コア機能仕様（要点）

### 3.1 認証情報（テンプレ/解決順）
- 認証情報は「ユーザー設定」＞「サーバー共有」の優先順で解決される
- 認証情報は暗号化して保存される
- 認証テンプレは chat / vision / imagegen を分離して保持できる
- 設定はファイルアップロード等により投入され、ファイルそのものは保存しない（保存するのは内容のみ）

確認観点（実装照合）：
- 共有状態でユーザー情報を削除しても共有解除されない（共有解除は別操作）
- “鍵が存在するか”は「復号できるか」で判定する（文字列有無ではない）
- provider/model が欠落・不正な場合のエラー文言/扱い

### 3.2 秘密ストア（自己修復・堅牢性）
- JSON破損時は空辞書で復旧し、運用を止めない
- `providers` 等のノードが dict でない場合は空dictへ自己修復して継続
- 削除系は例外を投げず False を返す（安全側）

確認観点：
- 破損JSONのバックアップ/復旧（最低限：継続できること）
- LWW（並列 put の勝者決定）の仕様が明確化されていること

### 3.3 スレッド文脈（Thread Context）
- スレッド単位で「会話キュー（文脈）」を保持する
- /ac_newtopic で文脈クリア
- /ac_summary で要約→文脈クリア（要約の残し方は仕様で定義する）
- /ac_loadtopic（将来）があるなら、「過去ログをどこまで読むか」「summary で中断するか」を仕様化する

確認観点：
- Bot 再起動後にスレッド管理が復元される（永続化の粒度）
- 削除済みスレッドIDのクリーンアップ方針（起動時等）

### 3.4 チャット実行ループ（Chat Loop）
- 1回の入力に対し、次の処理を行う：
  1) 入力検証
  2) 文脈収集（スレッド状態に従う）
  3) 認証解決（ユーザー＞サーバー）
  4) provider 呼び出し
  5) ツール（web検索/web読み取り 等）が必要なら起動
  6) 出力整形（必要なら redaction）
  7) スレッド文脈へ反映

確認観点：
- 継続（Continuation）のトリガ条件と終了条件
- ツール起動のガード（許可/禁止、無限ループ防止）
- 例外時に「簡潔なエラーを返す（詳細はログ）」の遵守

### 3.5 Web取得（検索/読み取り）
- Web検索は DuckDuckGo（ddgs）等を使用する
- Web読み取りは URL 取得→本文抽出→要約/回答 の手順
- 取得失敗時の扱い（タイムアウト/リトライ/禁止ドメイン等）を仕様化する

確認観点：
- web_read の入力/出力フォーマット
- URL正規化と、危険URL/追跡の扱い（必要なら将来仕様）

## 4. 旧コードと AI生成コードが混在する場合の確認手順（仕様→実装照合）

### 4.1 まず “仕様の正” を決める（この章が正）
- README やテストは「現状の挙動」を示すが、意図の仕様とは限らない
- まず本書で “あるべき” を定義し、次に実装差分を洗い出す

### 4.2 照合の粒度（最小→詳細）
1) 公開I/F（呼び出し元が依存する戻り値/例外/副作用）
2) 永続化の場所とデータ形式
3) 例外とログの扱い
4) edge-case（破損JSON、欠落provider、スレッド削除など）

### 4.3 照合成果物（後続で作る）
- 「仕様 vs 実装」差分表（モジュール別）
- 差分の分類：
  - 仕様の不足（仕様を更新すべき）
  - 実装バグ（実装を直すべき）
  - 仕様変更（方針決定が必要）
