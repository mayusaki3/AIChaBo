# 認証・秘密ストア仕様

本書は、AIChaBo コアにおける **認証情報（APIキー等）** と **秘密ストア（暗号化永続化）** の仕様を定義する。  

---

## 1. スコープ

対象：
- 認証情報の概念（chat / vision / imagegen）
- 認証情報の解決順（ユーザー設定／サーバー共有）
- 秘密ストアの永続化・暗号化・自己修復・削除堅牢化
- 共有（サーバー単位）を成立させるための最低限のルール

非対象：
- Discord コマンド仕様の詳細（UI層）
- 各 LLM プロバイダの API 仕様（AI層）
- Web取得の仕様（別文書）

---

## 2. 用語

- 認証テンプレート：利用者がアップロードする JSON/JSONC 形式の設定（chat/vision/imagegen）
- 認証情報：認証テンプレートから抽出され、内部で保持される provider/model/api_key 等
- ユーザー設定：特定ユーザーに紐づく認証情報
- サーバー共有：ギルド（サーバー）単位で共有された認証情報
- SecretStore：暗号化（Fernet）により認証情報等を永続化する機構
- 自己修復：永続データが破損/不正構造でも運用を止めずに継続できるよう補正する動作

---

## 3. 認証テンプレート仕様（概念）

### 3.1 セクション
認証テンプレートは、以下のセクションを持つ。

- chat：テキスト会話用
- vision：画像入力（説明/OCR等）用
- imagegen：画像生成用

各セクションは独立して provider/model を持てる。

### 3.2 最低限の論理フィールド（仕様）
- provider：利用プロバイダ名（例：OpenAI/Gemini/Claude）
- api_key：プロバイダ API キー（機密）
- model：モデル名（機密ではないが利用制限に影響）
- max_tokens：chatのみ（任意）
- その他：プロンプト上書き等（任意）

---

## 4. 認証情報の解決仕様（重要）

### 4.1 解決順（最優先ルール）
認証情報の解決順は以下で固定する。

1) ユーザー設定（user）
2) サーバー共有（server/guild）
3) どちらも無い場合は「未設定」として扱う

補足：
- ユーザー設定が存在する場合、サーバー共有が存在しても **ユーザー設定を優先**する。
- サーバー共有は「未設定のユーザーでも利用できる」ことが目的であり、上書きではない。

### 4.2 共有状態と削除の関係
- ユーザーが自分の認証情報を削除しても、サーバー共有は自動解除されない。
- 共有解除は明示的な操作として分離する（誤解除防止）。

---

## 5. 秘密ストア仕様（SecretStore）

### 5.1 目的
- APIキー等の機密情報を平文で保存しない
- 永続化データが破損しても、運用停止を避ける（自己修復）
- 削除系を含め、例外により UI/コマンド処理が停止しない設計とする

### 5.2 保存対象
最低限、次を保存できること。

- user 単位の provider→api_key 等
- server 単位の provider→api_key 等
- （将来）追加の機密情報（ただし本仕様では “任意拡張”）

### 5.3 暗号化
- Fernet により暗号化して保存すること
- master key は安全に保持されること（保存先の詳細は運用文書で定義してよい）
- 例外：master key を環境変数で与える方式がある場合でも、本仕様の整合性（復号可能性）が満たされればよい

### 5.4 自己修復（最低限）
破損/不正構造に対して、以下を満たす。

- JSON が破損して読み取れない場合：
  - 例外で停止しない
  - 最終的に「空の辞書」として扱い、運用継続する

- ノードが期待型（dict）でない場合：
  - 対象ノードを空 dict に再初期化し、処理を継続する

対象となるノード例（概念）：
- `users[<user_id>]["providers"]`
- `servers[<guild_id>]["providers"]`

### 5.5 “鍵が存在するか” の判定
- 文字列が存在するかではなく、「復号に成功するか」で判定すること
- 復号に失敗した値は “存在しない” 扱い（None/空）にする

### 5.6 削除系の堅牢化（重要）
- delete 系は例外を投げない
- 対象が欠落・空・保存失敗でも、呼び出し側が処理継続できる戻りを返す
  - 成功：True
  - 失敗：False（例外ではない）

### 5.7 並列 put（LWW）
- 同一キーに対する並列 put が起こり得る場合、最終状態が決定的であること
- 仕様としては **LWW（Last Write Wins）** を採用する
  - 「どちらが last か」を決める情報（例：timestamp）を持つこと
  - ただし、詳細の tie-break（同一時刻等）は実装側の決定性を満たす形でよい
- 本仕様の要求は「決定的であること」と「最終的に破損せず利用できること」である

---

## 6. エラー/例外ポリシー（コア共通）

### 6.1 コア層の原則
- UI層へ例外を伝播させない（停止させない）
- 例外はログに記録し、呼び出し側へは「安全な失敗（None/空/False）」を返す
- ただし、開発者の明確な誤り（必須引数欠落等）は ValueError 等で表現してよい
  - どの層で握りつぶすかは別文書（チャットループ仕様）で定義する

---

## 7. セキュリティ要件（最低限）

- api_key をログに出さない（redact が適用されること）
- 永続化は暗号化されること
- 共有認証の適用範囲が明確であること（ユーザー設定が優先）

---

## 8. 仕様-実装 照合ポイント（本書対応分）

- 解決順が「ユーザー＞サーバー共有」になっているか
- 共有状態と削除が独立しているか（自動解除されない）
- JSON破損時に空で復旧するか（停止しない）
- providers ノードが dict でない場合に自己修復するか
- delete が例外を投げず False を返すか
- 鍵存在判定が “復号できるか” か
- LWW が決定的か（結果が揺れないか）
