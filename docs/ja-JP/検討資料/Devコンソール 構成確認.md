# Discord / DevTools / Devコンソール 構成確認

## 結論
提示の(1)(2)(3)の分割は妥当。  
ただし「(3) Devコンソール」が **どこに常駐するか**（中央サーバーか、各ユーザーPCか）で責務境界が変わるため、役割を明確化しておくのが重要。

## 1. 想定構成（役割の整理）

### (1) Discord（スレッド + /ac コマンド）
役割：
- チャットUI（複数人で会話・指示・結果共有）
- 実行要求（ジョブ）発行、ステータス参照、承認（Plan/Apply）
- 実行結果（差分/ログ/次アクション）の共有

持たせない（推奨）：
- 実際のビルド/テスト/コード改変（任意コマンド実行）  
  ※安全性・環境差・秘密情報の観点

### (2) ユーザーローカル環境「あいちゃぼ DevTools」（Local Agent）
役割：
- ローカルworkspace操作（生成物の作成/編集、テスト実行、差分取得）
- 実行環境の責務（Node/Java/Python、SDK、社内NW、資格情報など）
- 実行結果を中央へ返す（ログ、diff、環境fingerprint）

性質：
- “実行者”であり、中央からの宣言的ジョブ（preset/action）を解釈して動く

### (3) あいちゃぼ Devコンソール（オーケストレーション + 生成）
役割：
- (1) と (2) の中継・統制（ジョブ作成、割当、進捗管理、結果集約）
- 生成物の品質保証（Gate判定、整合チェック、トレーサビリティ更新）
- コード/仕様/テストの生成（ただし「適用」はPlan/Applyで制御）
- 管理データ（WorkItem/Artifact/Link/Check/JobRun/Gate）の正（source of truth）

## 2. (3) Devコンソールの配置パターン（ここが要注意点）
### パターンA：中央サーバー（推奨：複数人共有に強い）
- Devコンソールは “中央” に常駐
- Discord Botと同居、または別サービス
- DevToolsは中央へポーリング/接続してジョブ受領

利点：
- 状況/メタデータの一元管理が容易
- 監査・権限・ゲート強制が簡単
- チーム全体で同じ状態を見られる

注意：
- 中央が生成を担う場合、秘密情報を入力させない設計が必須

### パターンB：各ユーザーPC（ローカルGUI/CLI）
- Devコンソールもローカルに置く
- Discordは“共有UI”だが、統制は各自で持つ

利点：
- オフライン/個別最適がしやすい
- 中央に機能を集めない

注意：
- 状態の一貫性（誰が最新を持つか）が難しい
- ゲートや権限が形骸化しやすい

## 3. 最小の修正提案（誤解を防ぐ定義）
提示(3)は「Devコンソール」というより、実態として以下2層に分けると混乱が減る。

- (3a) Devオーケストレータ（中央）：ジョブ・状態・ゲート・権限の正
- (3b) 生成エンジン（中央 or ローカル）：仕様/テスト/コードの生成  
  ※生成は中央でもよいが、適用はローカル（DevTools）でPlan/Apply推奨

## 4. 間違いやすい点（確認ポイント）
- (1) Discord上の自由文を、そのまま(2)がシェル実行しない（宣言的ジョブ化が必須）
- (3)が“何でも屋”になりやすいので、状態管理（正）と実行（ローカル）を分離
- ローカル実行結果には env fingerprint を必須化（再現性の説明責務）
