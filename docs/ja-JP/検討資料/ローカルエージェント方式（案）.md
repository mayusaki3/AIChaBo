# ローカルエージェント方式（案）

## 1. コンセプト
- Discord上の指示は「実行要求（ジョブ）」としてAIChaBoが受理する。
- 実行は各ユーザーPC（または各ユーザーが管理する開発VM）上の **AIChaBo Local Agent** が担当する。
- Agentはジョブを取得し、ローカルで工程（doc生成、テスト実行、差分提示など）を実施し、結果をDiscordスレッドへ返す。

## 2. 期待できるメリット
- 各ユーザー固有の開発環境で実行できる（SDK/依存、社内VPN、資格情報、GPUなど）
- リポジトリ巨大/ビルド重い場合でも、中央サーバー負荷を回避
- 秘密情報を中央へ集約せずに済む（ローカルの資格情報マネージャ等を利用可能）
- 生成物（差分・ログ）をユーザーの手元で確認しやすい

## 3. 主な課題（ここが設計の肝）
- 再現性：各自の環境差で結果が揺れる
- 安全性：Bot経由で任意コマンド実行に見えやすい（最重要）
- 監査性：誰が何を実行したか、結果が正しいか
- サポート：Agentの導入/更新/故障対応
- 信頼境界：Discordメッセージをそのまま「命令」として実行しない設計が必要

## 4. 推奨アーキテクチャ（責務分離）
### 4.1 中央（Discord Bot / Orchestrator）
- ジョブの受理・整形（ステップ定義、入力パラメータ）
- 実行ポリシー付与（許可操作、上限時間、対象workspace制約）
- Agentへの配布（キュー/ポーリング/プッシュ）
- 結果の受領とスレッド投稿（サマリ + 詳細）

### 4.2 ローカル（Local Agent）
- ローカルworkspace管理（対象repoのパス、ブランチ状態）
- “宣言”されたステップを実行（許可コマンドのみ）
- 差分抽出、ログ収集、成果物保存
- 実行結果を中央へ返却（署名付き）

## 5. 実行モデル（任意コマンド実行にしない）
- 「自由入力でシェルを叩く」ではなく、**ジョブは宣言的（DSL/JSON）** にする。
  - 例：{ action: "run_tests", tool: "pnpm", argsPreset: "test:coverage" }
  - 例：{ action: "generate_doc", template: "api_spec_md", inputs: {...} }
- Agentは “action + preset” を解釈し、内部の固定コマンドにマップする。
- どうしても任意コマンドが必要なら、段階的に：
  - /plan（差分・実行予定だけ表示）
  - /apply（ユーザーがローカルで明示承認）
  - を必須にする。

## 6. セキュリティ要件（最低限）
- Agentの実行権限はユーザー権限（管理者権限不要）
- 許可コマンド白リスト（git, pnpm, pytest, mvn 等）+ 引数制限
- 実行パス制限（workspace配下のみ）
- ネットワーク方針（原則制限、必要時だけ許可）
- 機密マスキング（ログ/差分に秘密が混入したら送信前に検知・遮断）
- “誰がそのAgentを操作できるか” を紐付け（Discord user_id と Agent登録鍵）

## 7. 信頼性・監査
- job_id、開始/終了時刻、対象repo、commit、実行ステップ、終了コード、主要ログ要約
- 結果に「実行時のcommit hash」と「差分パッチのhash」を含める
- Agent→中央の結果送信は署名（Agent登録時の鍵）で改ざん検知

## 8. 配布・更新
- Agentは自動更新が必要（互換性維持のため）
  - 例：中央が “required_agent_version” を提示し、古いAgentは実行を拒否
- OS別配布（Windows/MSI or zip、macOS、Linux）
- 設定は最小限（workspaceパス、許可プリセット、ログ保存先）

## 9. 現実的な最小導入（MVP）
- 方式：Agentが定期ポーリングで “自分宛ジョブ” を取得
- 機能：run_tests / git_diff_summary / generate_docs（テンプレ固定）だけ
- 権限：危険操作なし（push/merge/依存更新は不可）
- 返答：サマリ + 失敗時ログ抜粋 + 次アクションのみ

## 10. 判断基準（サーバー実行 vs ローカル実行）
- ローカルが有利：
  - 環境依存が強い、秘密が多い、ビルドが重い、社内NW要件が厳しい
- サーバーが有利：
  - 再現性重視、共通CI環境を前提、監査要件が強い、運用を単純にしたい
