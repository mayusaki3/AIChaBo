# 開発支援プラグイン（例）：Spec/Test/Impl Runner 概要

## 1. 背景・目的
- AIChaBo（Discord Bot）は、複数人の開発における「AIとのやり取りの共有」を起点にしている。
- 追加目的として、開発支援（仕様化・テスト設計・実装・検証の支援）を、Discord上の指示で一連の工程として実行し、結果（生成物・実行ログ・失敗理由・次アクション）をスレッドへ返す。

## 2. ゴール（このプラグインが提供する価値）
- Discordの1コマンドで、以下を“同一の作業単位”として扱えるようにする。
  - 要件整理 → 設計/ドキュメント生成 → テストケース生成 → 実行（lint/test/build等） → 結果コメント
- 生成物は「差分」「パス」「実行結果」「失敗時の再現手順」を必ず含め、複数人レビュー/引継ぎに耐える形にする。

## 3. 想定ユースケース
- 仕様のたたき台作成：issue/口頭要件を入力 → API仕様・I/F・例外・状態遷移を生成
- テスト仕様作成：API仕様を入力 → UT/IT/E2E観点とケースを生成
- 実装修正：既存リポジトリの特定ファイルを対象に修正 → テスト実行 → 結果報告
- リグレッション：特定機能のテストスイートを実行 → カバレッジ含めて報告

## 4. 前提と範囲（最初の版の現実的スコープ）
- Botが動作しているサーバー上で「作業ディレクトリ」を固定し、その配下で実行する（例：/opt/aichabo/workspaces/<repo>）。
- 外部I/F（Discord以外、SharePoint、CI連携など）は含めない（将来拡張）。
- 破壊的操作（push、release、DB migration適用など）はデフォルト禁止。実行可能にする場合は「明示的な承認ステップ」を必須化。

## 5. 概念アーキテクチャ（責務分離）
- Discordコマンド層（UI）
  - 受理、権限チェック、ジョブ起動、進捗通知、結果投稿
- Orchestrator（工程管理）
  - 工程定義（要件→設計→テスト→実行→報告）
  - 各ステップの入出力（成果物、ログ、失敗理由）を統一フォーマットで保持
- Workspace（実行環境）
  - リポジトリ/ブランチ/作業ディレクトリ
  - 生成物の保存、差分抽出、コマンド実行（テスト等）
- Policy/Security（安全装置）
  - 許可コマンド白リスト、パス制限、機密マスキング、実行タイムアウト
- Reporter（返答整形）
  - Discordへ返すコメントを、短縮サマリ + 詳細（ログ/差分/次手順）に整形

## 6. プラグインI/F（例）
### 6.1 Discordコマンド（例）
- /ac_spec_run
  - 入力：要件テキスト、対象リポジトリ、対象モジュール、出力先docsパス
  - 出力：仕様md（差分）+ 実行結果コメント
- /ac_test_run
  - 入力：仕様mdのパス or テキスト、出力先tests仕様パス
  - 出力：テスト仕様md（差分）+ 実行結果コメント
- /ac_impl_run
  - 入力：対象ファイル/範囲、やりたい修正、実行するテストコマンド
  - 出力：コード差分 + テスト結果 + 失敗時の原因候補
- /ac_job_status
  - 入力：job_id
  - 出力：進捗、現在ステップ、直近ログ抜粋

### 6.2 Orchestratorのステップ（例：固定パイプライン）
1) 要件整形（Requirements）
2) 設計/ドキュメント生成（Design/Docs）
3) テストケース生成（Test Design）
4) 実行（Lint/Test/Build）
5) 報告（Report）

※ステップは「スキップ可」にしつつ、スキップ時は理由を記録する。

## 7. 実行方式（“サーバー上で実行”を成立させる設計ポイント）
- 実行は「サンドボックス方針」を前提にする
  - 実行可能コマンド：事前定義された白リストのみ（例：git diff、pytest、mvn test、pnpm test 等）
  - 実行ディレクトリ：workspace配下のみ
  - ネットワーク：原則遮断（必要な場合は例外化し、監査ログ対象）
  - タイムアウト：各工程/各コマンドに上限
- 成果物はすべて workspace 配下に保存し、パスを結果に含める
- 生成物は「差分」を必須で出す（レビュー容易性のため）

## 8. 返答フォーマット（Discordへ返すコメントの最小要件）
- 1) 実施概要（何を、どのworkspaceで、どのブランチ/コミットを基点に）
- 2) 変更点サマリ（ファイル一覧、行数、影響範囲）
- 3) 実行結果（コマンド、終了コード、成功/失敗、主要ログ抜粋）
- 4) 生成物リンク/パス（docsやテスト仕様の保存先）
- 5) 次アクション（レビュー観点、残タスク、追加で回すべきテスト）

## 9. 権限・承認（複数人運用での最低限）
- 役割例
  - Admin：workspace登録、ポリシー変更、危険コマンド許可
  - Maintainer：通常実行（spec/test/impl）、ブランチ作成まで
  - Viewer：結果閲覧のみ
- 破壊的操作（例：push、merge、タグ作成、依存更新の自動適用）は承認ステップ必須
  - 例：/ac_impl_run --plan で差分だけ提示 → /ac_impl_run --apply で適用

## 10. 監査ログ（後追い可能性）
- job_id、起動者、対象repo、対象ブランチ、実行コマンド、終了コード、生成物ハッシュ、主要ログの要約
- 機密の取り扱い
  - APIキー等はログ・返答に出さない（マスキング）
  - 生成物中に混入しないよう、プロンプト側でも禁止事項を明記

## 11. テスト観点（プラグイン自身の品質保証）
- UT（例）
  - 入力バリデーション（危険コマンド拒否、パス逸脱拒否）
  - ステップ遷移（成功/失敗/スキップ）
  - レポート整形（必須項目が欠けない）
- IT（例）
  - ダミーworkspaceで、実コマンド（echo/pytestの短いもの）を流して end-to-end に近い検証
- テストID例（AIChaBo流に合わせる場合）
  - COMMON-PLUGIN:T01-01-01 入力が空 -> エラー
  - COMMON-PLUGIN:T01-02-01 許可されないコマンド -> 拒否
  - COMMON-PLUGIN:T02-01-01 job実行 -> 成功サマリを返す

## 12. 今後拡張（ロードマップ例）
- コマンドのテンプレート化（プロジェクト別に “工程定義” を差し替え）
- PR作成までの自動化（ただし merge は承認必須）
- リポジトリ横断の成果物保存（docs生成物の集約、検索）
- CI連携（CI結果を取り込み、Discordへ要約）
